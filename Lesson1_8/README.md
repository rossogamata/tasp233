## 1. Вступ: від контейнера до застосунку

На попередніх заняттях ми запускали окремі контейнери за допомогою `docker run`. Реальний застосунок зазвичай складається з кількох компонентів: вебінтерфейсу, API, бази даних, кешу та фонового обробника. Для їхньої роботи потрібно узгодити образи, порти, мережі, змінні середовища, постійні дані та порядок готовності.

Керувати кожним контейнером окремою командою незручно: команди складно відтворювати, передавати іншій людині та підтримувати після змін. Compose дає змогу описати застосунок у конфігураційному файлі. Оркестратор додатково керує бажаним станом сервісів у кластері машин.

## 2. Поняття Docker Compose

**Docker Compose** — інструмент для опису та запуску багатоконтейнерного застосунку. Конфігурацію зазвичай записують у YAML-файл `compose.yaml`, а сучасний Compose запускають як підкоманду Docker CLI: `docker compose`.

### 2.1 Основні поняття

| Поняття | Значення |
|---|---|
| **Project** | Сукупність сервісів і пов'язаних із ними ресурсів, описаних Compose-файлом |
| **Service** | Опис ролі контейнера: образ або збірка, параметри запуску, мережі та інші налаштування |
| **Container** | Запущений екземпляр сервісу |
| **Network** | Канал зв'язку між контейнерами; сервіси в одній Compose-мережі можуть знаходити один одного за іменем |
| **Volume** | Постійне сховище, життєвий цикл якого не обмежується одним контейнером |
| **Environment** | Налаштування, передані процесу контейнера через змінні середовища |
| **Healthcheck** | Перевірка готовності або працездатності контейнера |

### 2.2 Приклад `compose.yaml`

Приклад описує вебсервер і API: вебсервер доступний з хоста на порту `8080`, а API має внутрішній порт `8000`. Він демонструє структуру сервісів, мережу та перевірку готовності; NGINX у цьому прикладі не налаштований як proxy до API.

```yaml
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      api:
        condition: service_healthy
    networks:
      - app-network

  api:
    image: python:3.12-alpine
    command: ["python", "-m", "http.server", "8000"]
    expose:
      - "8000"
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/').read()"]
      interval: 10s
      timeout: 3s
      retries: 3
    networks:
      - app-network

networks:
  app-network:
```

Ключові поля:

| Поле | Призначення |
|---|---|
| `image` | Образ, із якого створюється контейнер |
| `build` | Каталог із `Dockerfile` для побудови власного образу |
| `ports` | Публікація порту у форматі `порт_хоста:порт_контейнера` |
| `expose` | Опис внутрішнього порту без публікації його на хості |
| `environment` | Передавання змінних середовища |
| `depends_on` | Опис залежності сервісів; сам по собі не гарантує готовності залежного застосунку |
| `healthcheck` | Перевірка стану контейнера; може використовуватися разом з умовою `service_healthy` |
| `networks` | Під'єднання сервісу до мережі |
| `volumes` | Монтування постійних даних або файлів |

У цьому демонстраційному прикладі `api` запускає вбудований HTTP-сервер Python. Compose-сервіси зазвичай знаходять один одного за DNS-іменем сервісу: API доступний для іншого сервісу за адресою `http://api:8000`. `localhost` усередині контейнера вказує на цей самий контейнер, а не на сусідній.

### 2.3 Типовий цикл роботи

```bash
# Перевірити та нормалізувати конфігурацію
docker compose config

# Запустити проєкт (Compose збере сервіси, для яких задано build)
docker compose up --detach

# Перевірити стан контейнерів і переглянути логи
docker compose ps
docker compose logs --follow

# Зупинити та прибрати контейнери й мережу проєкту
docker compose down
```

`docker compose stop` зупиняє контейнери, але не видаляє їх. `docker compose down` видаляє контейнери й мережу проєкту; іменовані volumes зазвичай залишаються, якщо явно не вказати `--volumes`. Дані важливих сховищ перед очищенням потрібно зберегти.

### 2.4 Для чого Compose підходить

- локальна розробка та навчальні стенди;
- інтеграційне тестування кількох сервісів;
- відтворюваний запуск застосунку на одній машині;
- передавання командам зрозумілого опису середовища.

Compose описує й запускає проєкт, але сам по собі не перетворює кілька машин на кластер і не забезпечує кластерне відновлення сервісів.

## 3. Поняття оркестрації контейнерів

**Оркестрація контейнерів** — автоматизоване керування розміщенням і життєвим циклом контейнерних сервісів. Оркестратор зіставляє поточний стан із бажаним станом, заданим користувачем.

Типові можливості оркестратора:

- запуск потрібної кількості екземплярів сервісу;
- розміщення навантаження на доступних вузлах;
- перезапуск або перепланування завдань після збою;
- внутрішнє виявлення сервісів і балансування навантаження;
- поступове оновлення та відкат розгортання;
- керування мережами, конфігураціями та секретами.

Оркестрація не усуває потреби у моніторингу, резервному копіюванні, безпечному налаштуванні мережі та проєктуванні застосунку. Наприклад, автоматичне перезапускання контейнера не гарантує збереження даних, якщо їх записували лише у файлову систему цього контейнера.

### Приклад бажаного стану

Оператор задає: «Сервіс `web` має працювати у трьох екземплярах». Оркестратор стежить, щоб доступні завдання відповідали цій кількості, і за певних умов створює заміну для завдання, що завершилося. Це не означає, що всі помилки застосунку будуть автоматично виправлені: оркестратор відновлює процеси відповідно до політик, але не виправляє дефекти коду чи даних.

## 4. Поняття Docker Swarm

**Docker Swarm mode** — режим кластерної оркестрації, вбудований у Docker Engine. Кластер Swarm складається з вузлів (**nodes**), які запускають сервіси як завдання (**tasks**).

### 4.1 Архітектура та терміни

| Термін | Пояснення |
|---|---|
| **Node** | Машина з Docker Engine, приєднана до Swarm |
| **Manager** | Вузол, що керує станом кластера та розміщенням завдань; також може запускати завдання |
| **Worker** | Вузол, який отримує від manager завдання та виконує їх |
| **Service** | Опис бажаного стану застосунку: образ, кількість реплік, порти, обмеження та політики оновлення |
| **Task** | Окрема запланована одиниця роботи сервісу, зазвичай контейнер |
| **Stack** | Група пов'язаних сервісів, розгорнутих разом |

Для стійкості керівної площини рекомендується непарна кількість manager-вузлів. Raft-консенсус потребує кворуму: якщо менеджери втратили кворум, наявні завдання можуть продовжити роботу, але керування кластером і зміна бажаного стану будуть обмежені.

### 4.2 Основні властивості Swarm

- **Бажаний стан і reconciliation:** manager намагається підтримувати задану кількість реплік.
- **Масштабування:** кількість реплік сервісу можна змінити командою.
- **Розміщення завдань:** scheduler призначає завдання доступним вузлам з урахуванням стану й обмежень.
- **Виявлення сервісів:** сервіси спілкуються через імена в мережі Swarm.
- **Overlay network:** з'єднує сервіси на різних вузлах кластера.
- **Routing mesh:** опублікований порт сервісу може приймати трафік на вузлі кластера й маршрутизувати його до завдання сервісу.
- **Rolling update:** оновлення можна виконувати поступово, задаючи параметри оновлення.
- **Secrets і configs:** передавання чутливих даних та конфігурацій сервісам відповідними механізмами Swarm.

> Swarm не зберігає стан застосунку замість нього. Для бази даних потрібні продумане сховище, резервні копії та план відновлення.

### 4.3 Демонстрація Swarm на одному вузлі

Одновузловий Swarm дає змогу показати команди й бажаний стан, але **не демонструє відмовостійкість між машинами**.

```bash
# Ініціалізувати Swarm на локальній машині
docker swarm init

# Переглянути стан вузлів
docker node ls

# Створити сервіс із трьома репліками та опублікувати порт
docker service create \
  --name web-demo \
  --replicas 3 \
  --publish published=8088,target=80 \
  nginx:alpine

# Переглянути стан сервісу й розміщення завдань
docker service ls
docker service ps web-demo

# Змінити бажану кількість реплік
docker service scale web-demo=2
docker service ps web-demo

# Видалити сервіс і залишити Swarm
docker service rm web-demo
docker swarm leave --force
```

Команда `docker swarm init` створює Swarm із локальної машини як manager. Для приєднання інших вузлів `docker swarm join-token worker` або `docker swarm join-token manager` показує команду приєднання з токеном. Токен — секрет: не публікуйте його у відкритих матеріалах або скриншотах. Для реального кластера вузли мають мати відповідну мережеву доступність; не відкривайте необхідні порти інтернету без обмежень і безпекової оцінки.

Щоб керувати кількома пов'язаними сервісами як stack, можна використати файл сумісного Compose-формату:

```yaml
services:
  web:
    image: nginx:alpine
    ports:
      - "8088:80"
    deploy:
      replicas: 3
      update_config:
        parallelism: 1
        delay: 10s
      restart_policy:
        condition: on-failure
```

```bash
docker stack deploy --compose-file compose.yaml lesson
docker stack services lesson
docker stack ps lesson
docker stack rm lesson
```

`docker stack deploy` використовує Compose-файл, але підтримує не всі можливості сучасної Compose Specification. Зокрема, `build` не збирається командою stack deploy: образи потрібно підготувати заздалегідь і зробити доступними вузлам, наприклад через registry. Перед демонстрацією слід перевірити сумісність конкретної конфігурації з установленою версією Docker Engine.

## 5. Docker Compose і Docker Swarm: порівняння

| Ознака | Docker Compose | Docker Swarm |
|---|---|---|
| Типове середовище | Одна машина | Кластер вузлів |
| Основна команда запуску | `docker compose up` | `docker service ...` або `docker stack deploy` |
| Основна одиниця опису | Сервіс Compose-проєкту | Сервіс Swarm із завданнями |
| Масштабування | Кілька локальних екземплярів у межах одного середовища | Репліки, які scheduler розподіляє між вузлами |
| Самовідновлення | Налаштовується для контейнерів на одній машині; кластерного scheduler немає | Manager підтримує бажану кількість завдань на вузлах кластера |
| Мережа | Переважно локальні bridge-мережі | Overlay-мережі між вузлами та routing mesh |
| Основний сценарій | Розробка, тестування, навчання, запуск на одній машині | Простіший кластерний запуск контейнерних сервісів |
| Важливе обмеження | Не є багатовузловим кластерним оркестратором | Потребує налаштування та адміністрування кластера; має вужчу екосистему, ніж деякі альтернативи |

Compose і Swarm не є взаємовиключними поняттями: YAML допомагає описати сервіси, але команди запуску та підтримувана семантика відрізняються. Не слід вважати, що будь-який файл, який працює з `docker compose up`, без змін матиме ідентичну поведінку через `docker stack deploy`.

### Як обрати інструмент

- Потрібно швидко запустити залежності застосунку на ноутбуці — **Docker Compose**.
- Потрібно ознайомити групу з базовими поняттями кластера на Docker Engine — **Docker Swarm**.
- Для production-рішення вибір роблять після оцінки вимог до масштабування, доступності, мережі, зберігання даних, безпеки, моніторингу, компетенцій команди та підтримки платформи.

## 6. Питання для обговорення та перевірки розуміння

1. Яку проблему розв'язує Compose порівняно з набором ручних команд `docker run`?
2. Чому сервіс `api` у прикладі може бути доступний для `web` без публікації його порту на хості?
3. Чому `depends_on` без перевірки healthcheck не завжди означає, що залежний застосунок уже готовий?
4. У чому різниця між контейнером, сервісом і task у Swarm?
5. Що відбудеться з кількістю завдань, якщо бажано три репліки, а одна з них завершується?
6. Чому запуск трьох реплік на одному вузлі не забезпечує стійкості до відмови цього вузла?
7. Чому `docker stack deploy` може потребувати попередньо зібраного та опублікованого образу?
8. Які дані потрібно винести з контейнера, щоб не втратити їх після заміни завдання?

## ✅ Підсумок

Docker Compose описує взаємопов'язані контейнери й робить зручним їхній відтворюваний запуск переважно на одній машині. Оркестрація керує сервісами відповідно до бажаного стану, зокрема в кластері. Docker Swarm додає до Docker Engine кластерні вузли, планування завдань, масштабування, overlay-мережі та механізми оновлення. Вибір інструмента залежить від потрібного масштабу й операційних вимог, а не лише від кількості контейнерів.
